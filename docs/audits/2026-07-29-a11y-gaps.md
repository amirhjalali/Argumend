## 2. Images and meaningful SVGs without alt text

- **Zero `<img>` tags** in `app/` or `components/` — the app uses `next/image` or CSS
  backgrounds, so there is no raw-`<img>` alt-text surface.
- Decorative inline `<svg>` coverage is otherwise complete: a full multi-line parse of
  every `<svg …>` open tag found exactly **one** without `aria-hidden` / `role` /
  `aria-label`: `components/ShareVerdictCard.tsx:448` (the X/Twitter glyph). **FIXED** —
  added `aria-hidden="true"` (the button already reads "Post on X").
- `components/ScalesOfEvidence.tsx:177` is the one *meaningful* SVG and correctly uses
  `role="img"` + a computed `aria-label`. Good pattern; reuse it for
  `components/ConfidenceGauge.tsx`, `components/ConfidenceTimeline.tsx`,
  `components/DiamondDiagram.tsx` and `components/MiniGraphPreview.tsx`, which render
  data-bearing SVGs with no text alternative at all (a sighted user reads a value; a
  screen-reader user gets nothing). Not fixed — writing a correct alternative requires
  deciding what each chart's one-sentence summary should be, which is a content call.

## 3. Keyboard-navigation gaps (structural — reported, not fixed)

| Component | Escape | `role="dialog"` / `aria-modal` | Focus trap | Focus restore |
|---|---|---|---|---|
| `components/SearchModal.tsx` | yes (`case "Escape"`, line 431) | yes (486–487) | **no** | not observed |
| `components/CruxModal.tsx` | **no** | yes (41–42) | **no** | not observed |
| `components/EmbedButton.tsx` | yes (line 36) | `role="dialog"` w/o `aria-modal` (line 72) | n/a (popover) | not observed |
| `components/GlossaryTerm.tsx` | yes (line 64) | none | n/a (popover) | n/a |

Three structural issues, in priority order:

1. **`CruxModal` declares `aria-modal="true"` but has no Escape handler.** It is
   dismissable only by clicking the close button or backdrop. Announcing a modal to AT
   and then not honouring Escape is the worst combination — a keyboard user who opens a
   crux from `RichNode` has no keyboard exit. This is the highest-value fix here.
2. **No focus trap in either modal.** With `aria-modal="true"` set, AT hides the
   background from the virtual cursor, but Tab still walks into the (visually obscured,
   still-focusable) page behind the overlay. Needs a proper trap + focus restore to the
   invoking element on close. Deliberately not attempted here — a hand-rolled trap is
   easy to get subtly wrong and this is live canvas code.
3. **`EmbedButton` popover uses `role="dialog"` without `aria-modal`.** Semantically it
   is a non-modal disclosure; `role="dialog"` overstates it. Either add `aria-modal` and
   real modal behaviour, or drop the role and rely on `aria-expanded` on the trigger.

`SearchModal` is otherwise the strongest of the three — it wires
`aria-expanded` / `aria-controls` / `aria-activedescendant` on the combobox input and
gives each result a stable `id`. It only lacks the trap.

## 4. Off-palette colour that escapes the existing guard

The repo-wide guard in `lib/categoryColors.test.ts` matches only
`/(amber|yellow|tangerine|indigo|sky|violet)-[0-9]/` — i.e. **named Tailwind utilities
with a numeric shade**. Four whole classes of colour bypass it:

**(a) Arbitrary Tailwind values.** `bg-[#f59e0b]` contains no banned word, so it passes.
The codebase leans heavily on this form (`bg-[#302e2a]`, `border-[#3d3a36]`, …), so it
is a live regression path, not a theoretical one. Current arbitrary-hex usage is
on-palette; nothing to fix, but the guard should be extended.

**(b) Hex literals in `style={{…}}` / JS objects.** Not scanned at all. Off-palette
literals currently present:

| File | Value | Verdict |
|---|---|---|
| `app/perspectives/page.tsx:102` | `accentColor: "#6b5b95"` (violet) | **Real violation.** `lib/variantStyles.ts:84` documents retuning this exact hex off violet to on-brand stone, and `lib/variantStyles.test.ts` bans it — but only within `lib/`. The same hex survived in `app/`. Not fixed (excluded path). |
| `components/icons/LLMIcons.tsx:99,107` | `color: "#10B981"` (emerald) | Off-palette green used as a provider identity colour. Arguably intentional brand-marking; worth a decision. |
| `components/icons/LLMIcons.tsx:100,108` | `bgLight: "#D1FAE5"` (emerald-100) | Same. |
| `components/icons/LLMIcons.tsx:115–116` | `#4285F4` / `#DBEAFE` | Google brand blue — legitimate as a third-party mark. |
| `app/auth/signin/page.tsx:58,66,70` | `#4285F4` / `#FBBC05` / `#EA4335` | Google "G" logo fills. Legitimate; must not be re-tinted. |
| `app/global-error.tsx:54,61` | `#fef2f2` / `#ef4444` | Semantic error red in the framework-level error boundary (which cannot use Tailwind). Acceptable, but should be the palette's `#a23b3b` family for consistency. |

**(c) The guard's scope excludes `lib/`, `hooks/`, and `data/`.** Only `app/` and
`components/` are walked.

**(d) `green` / `emerald` are not banned repo-wide.** They are banned *only* in the six
SOT-migrated files. There is substantial surviving emerald elsewhere —
`app/analysis/[id]/AnalysisView.tsx` (lines 120, 215–216, 459, 498–499),
`components/MobileArgumentList.tsx` (31, 72, 79, 115, 180–183, 279),
`components/JudgingResults.tsx:291`, `components/VerdictVoting.tsx:346`,
`components/ShareVerdictCard.tsx:430–431`, `components/ShareToMoltbook.tsx:251`,
`components/ControversyMeter.tsx:47`. Several of these are exactly the
"green = this claim is true" verdict signal the SOT migration exists to kill —
`MobileArgumentList.tsx:279` maps `settled: "bg-emerald-100 text-emerald-700"`, which is
the *same* pattern the guard already forbids in `app/dashboard/page.tsx`. This is a
follow-up migration, not a mechanical find-and-replace, so it was left alone.

### Recommended guard hardening

Extend `lib/categoryColors.test.ts` (or add a sibling test) to also:

- scan `lib/` and `hooks/` alongside `app/` and `components/`;
- match arbitrary values: `/\[#(f59e0b|fbbf24|d97706|eab308|facc15|6366f1|0ea5e9|8b5cf6|f97316)\]/i`, or
  better, allow-list hexes against the documented palette rather than deny-listing;
- match bare hex literals in the same allow-list pass, with a small explicit exemption
  set for third-party brand marks (Google `#4285F4`/`#FBBC05`/`#EA4335`, X `#0f1419`).

An allow-list is the right shape here: the deny-list is unbounded, and every gap above
is a hex the deny-list simply never thought to name.
