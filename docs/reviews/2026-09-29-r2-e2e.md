# Round 2: end-to-end tests in CI (2026-09-29)

Branch `r2/e2e`. Before this, nothing drove the built site in a browser. The ~2,900 vitest
tests render components in happy-dom, and `scripts/smoke-standalone.mjs` only checks HTTP.
A regression like "the diagram is blank on phones" or "the header scrolls away" would have
shipped without failing anything.

## What changed

- `@playwright/test` 1.63.0 is a devDependency, pinned exactly (Node >=20). `bun.lock` gains
  3 packages. There is a new script, `bun run test:e2e`.
- `e2e/` holds the config, one fixtures file and 7 spec files: 30 tests across the two projects.
- CI has a new `e2e` job beside `check` (details under "CI" below).
- Shared files, one or two lines each:
  - `vitest.config.mts` excludes `e2e/**`.
  - `eslint.config.mjs` ignores `playwright-report/**` and `test-results/**`. The HTML report
    ships the trace viewer's JS, and eslint would otherwise lint it after a failed local run.
  - `.dockerignore` drops `e2e/`.
  - `productionPackaging.test.ts` checks the CI wiring (the new job, the `test:e2e` script,
    the vitest exclude, and that the server runs offline).
- One app change: `data-testid="home-primary-cta"` on home's rust button in
  `components/home/HomeLanding.tsx`. No other selector needed one. The suite uses roles and
  accessible names, plus hooks that already existed: `data-crux-sheet`, `#agreement`,
  `data-testid="topic-diagram"`, and React Flow's `.react-flow__node`.

## What the suite covers

There are two projects:
- `desktop`: 1440×900.
- `phone`: 390×844, `isMobile`, `hasTouch`, Chromium.

Every browser test also runs two guards when it finishes:
- **Third-party requests.** It blocks and records any request that leaves the server's host,
  and fails if there was one.
- **Console errors.** It fails on any console error or uncaught page error. That is where
  hydration mismatches show up in a production build.

## Runtime and flakiness

The suite was run against a production build of this branch every time:

| Run | Result |
|---|---|
| Config-started `next start`, 5 workers | 30/30 in 9.7s. Again at 30.6s while other agents loaded the machine. |
| CI mode (`CI=1`, 2 workers, retries 1), against the standalone server | 30/30 in 12.2s |
| CI mode, `--repeat-each=3`, 2 workers | 90/90 in 36s, nothing retried |
| `--repeat-each=4`, 8 workers | 120/120 in 46.7s |

In GitHub the job's time will be dominated by install, the Chromium download and the build. The
tests themselves should take well under a minute. **This has not run on GitHub yet**, because
the branch was never pushed.

What keeps it stable:
- **Hydration.** `waitForHydration()` waits for React to attach props (`__reactProps$…`) before
  clicking a client control. Without it, a click that lands before hydration is silently lost.
  This relies on a React internal that has been stable from React 17 to 19. If a React upgrade
  renames it, `fixtures.ts` is the one place to change.
- **The ⌘K shortcut toggles** the dialog, so the test presses it again only while the dialog
  is still closed.
- **One fixed wait.** It is in the scroll-lock check, which asserts that something did *not*
  happen, and a control assertion right after it proves that wheel input does work.
- **Offline server.** It runs with no database, no provider keys and every live flag off, the
  same env as the smoke script.

I checked that the guards can actually fail:
- The overflow helper flags an injected 2000px element. `html` and `body` clip overflow-x, so
  the document's own scroll width never shows it.
- The request guard records a CSP-allowed `images.unsplash.com` request.
- The console guard fails on `console.error`.

## CI

The new `e2e` job in `.github/workflows/ci.yml` runs on push to main and on PRs, like `check`.
Its steps:
1. Check out, set up Bun 1.3.14, and set up Node 20 from `.node-version` (production runs the
   standalone server on Node 20).
2. `bun install --frozen-lockfile`.
3. `bunx playwright install --with-deps --only-shell chromium`.
4. `bun run build`, with no env, like `check`.
5. `bun run test:e2e`.
6. On failure, upload `playwright-report/` and `test-results/` as an artifact, kept 14 days.

How the config picks a server:
- **`E2E_BASE_URL` is set:** it tests that server and starts nothing.
- **`bun run build` assembled the standalone package** (CI, or a normal checkout): it starts
  `node .next/standalone/server.js` on `E2E_PORT` (default 3290).
- **Only `.next` exists** (a worktree): it starts `next start` on the same port.

`reuseExistingServer` is off, so a busy port fails the run instead of silently testing another
checkout's build.

`scripts/smoke-standalone.mjs` is left as it is: it covers the debate and judge APIs, and
`productionPackaging.test.ts` checks its contents. The e2e config reuses its offline env.

## Running it locally

```
bun --bun next build                       # in a worktree; `bun run build` elsewhere
bun run test:e2e                           # starts the server itself on :3290
E2E_BASE_URL=http://127.0.0.1:3026 bun run test:e2e   # or test a server already running
E2E_CHROMIUM_PATH=/path/to/chrome-headless-shell bun run test:e2e   # skip `playwright install`
```

## Left, and why

- **Not covered:**
  - Dark mode, axe accessibility scans and visual snapshots: the a11y/dark agent owns that area,
    and pixel baselines would be brittle this week.
  - `/reply` and the live lanes: they are off in production.
  - Browsers other than Chromium: it keeps CI fast.
- **Port.** Locally, port 3026 was already taken by another agent's baseline server, so I used
  3926 and 3927. I stopped both when done.
- **Shared `node_modules`.** This worktree's `node_modules` is a link to the main checkout's.
  So that other agents' installs were not disturbed, I copied the three Playwright packages in
  (additive) and linked `.bin/playwright`, instead of running `bun install` through the link.
  A later `bun install` from main's lockfile may prune them until this branch merges.
