# Filter C re-scoring: are the changed reports better, or just different?

Status: decision support for the founder on `CRUX_PROJECTION_SKIP_UNCONTESTED` (filter C, `lib/crux/projectionFilter.ts`). Companion to `docs/reviews/2026-09-15-crux-levers-evidence.md` §4, which showed *which* reports change; this doc asks whether the changed ones are better by `docs/evals/disagreement-diagnosis-rubric.md`. No code was changed and no model was called: every report below is a stored extraction replayed through the real `projectDisagreementReport` with the flag off and on.

## Method

- Replay: a scratch copy of `scripts/crux-lever-projection-diff.ts` (live-replay half only) dumped the full flag-off and flag-on reports for all 40 sonnet reports in `.eval-runs/sources-2026-09-15T02-22-03-636Z` and all 12 opus reports in `.eval-runs/sources-2026-09-15T17-22-48-563Z`. Flag-off replay reproduced the stored crux list in 40/40 and 12/12.
- Scoring: both versions of each changed report scored on the rubric's seven dimensions (0–2, 14 max) following the conventions of the three checkpoint reviews (crux 2 = the proposition a careful human would say the argument turns on; resolution docked to 1 for filler such as "The source does not state what would settle this" or an "agree on the disagreement" path; type judged on what the reader sees). The reviewers' notes in `docs/reviews/2026-09-15-v2-checkpoint-evidence/sonnet-sources-run1-part1.md`, `...-part2-and-flagship-corpus.md` and `sources-model-comparison-runA-vs-runB.md` (Run A = the opus directory) were used to decide what the load-bearing crux is.
- What "off" means here. The projection has moved since the runs were stored (common-ground attestation, the `value-conflict` / `priority-tradeoff` patterns, the `single-empirical-crux` guard). So "off" is today's code with the flag off, not the stored report: in 10 of the 12 changed reports the flag-off pattern or headline already differs from what the reviewers scored (for example `same-conclusion-different-reasons` is already `value-conflict`, no longer the rubric-letter hard fail). Scores are off-vs-on under today's code; the reviewer's original total is listed as a reference only.
- Two replay limits. The stored files hold no claim stakes, so the replay's accountability box is always empty; stake effects below were read from the stored originals instead. And the attestation rule now drops single-quote common ground in 17/40 sonnet and 5/12 opus replays, so reason (i) ("explicit common ground in the report") fires on only one live report; everything else is reason (ii) ("no position disputes it").

## Hard-fail deltas

- Removed: `mixed-value-and-empirical` (sonnet). Under today's code with the flag off, the user-visible insight, summary and share subheadline still say the argument turns on "Is this true: In the pilot, the model flagged 30 candidates", beneath a `value-conflict` headline. That is the reviewer's "clearest value-for-empirical swap in the batch", and it is the one remaining hard-fail candidate among the 12 changed reports. With C on, the figure leaves every user-visible field.
- Not C's doing: the other two run-1 hard fails (`explicit-update-commitment` sonnet, `same-conclusion-different-reasons`) are already fixed in the flag-off replay by the pattern work that landed after the run (`priority-tradeoff`, `value-conflict`). C does not touch the sonnet `explicit-update-commitment` report.
- None introduced in the diagnosis layer. The three primary-type changes are empirical ↔ causal ↔ procedural, never value ↔ empirical: `causal-model-split-downtown` causal → empirical (an overclaiming headline, not a swap), `claim-stake-prompt-injection` empirical → causal (a fix), `claims-with-source-evidence` procedural → empirical (a fix), `mixed-value-and-empirical` normative → procedural (the `value-conflict` label the reviewer wanted is lost, but the crux it framed was the swap).
- One borderline case inside the crux box only: `explicit-update-commitment` (opus). The pattern stays `priority-tradeoff` and the crux is still typed `priority`, but the primary crux's resolution condition becomes an evidence check ("Sales records comparing…") on a weighing question. A reader who follows the crux box would be told a value tradeoff is settled by sales records.

- Sonnet: 32 of 40 unchanged. For every one, the flag-on crux array is byte-equal to the flag-off array, the whole report is byte-equal except `provenance.generatedAt`, and the filter emitted zero warnings (no `Projection skipped engine crux` line on any of the 32).

- On the 12 changed reports the filter's only footprint outside the crux list is the skip warning(s) in `quality.warnings` and whatever the diagnosis derives from the new primary (pattern, headline, insight, summary, share subheadline, resolvability band in two cases: `sarcasm` high → medium, `bus-route` medium → high).

## Recommendation

**Turn filter C on.** Under today's code the changed reports are better in 8 of 12, the same in 3, worse in 1; off 141 → on 149 over the twelve; the one remaining hard-fail candidate among them disappears; no hard fail appears; three reviewer-named wrong primaries (downtown comparison, mandate causation, participation-undermines-gap) become the reviewer's own crux; the box never empties; and the 40 unchanged reports are byte-identical bar a timestamp. It also changes nothing on the 64 fixtures, so the fixture eval carries no risk here.

If a tweak is wanted, the one worth naming is not in the filter: when a crux borrows its question from a disagreement candidate, take that candidate's resolution condition before the claim's own (`projectReport.ts` currently prefers `claim.resolution.condition`). That is what turned the opus `explicit-update-commitment` primary from "agree how to weigh embeddedness against sales" into "check the sales records". It would also have removed the `sarcasm` and `mixed-value` template resolutions. It has not been replayed, and it alters flag-off output, so it is a separate change, not a condition on C.

Risks, plainly:

1. The replacement primary is sometimes the next best of a weak set: `bus-route` still leads with the agreed metric question (now on Tomas's claim), `mixed-value` leads with a near-restatement of the main question. C moves these from wrong to mediocre, not to right.
2. The conservative "opposes counts as dispute" rule is what makes C safe (it never empties a box), and it is also why the one regression happens: an accepted fact wired as opposing a position survives and becomes primary (`c-sales`). The `--loose` alternative in the evidence doc is worse (empties three boxes).
3. An empirical replacement primary flips the pattern to `single-empirical-crux` regardless of how many disagreements the report lists (`causal-model-split-downtown`). That guard was removed deliberately in `lib/disagreement/diagnosis.ts`; C makes it fire once more. Not a swap, but a headline that overclaims.
4. Three replacement primaries have no participant stake in the stored extraction (`c-mandate-caused`, `c-warning`, `c-door-to-door`), so the live pipeline would mint a participant-less fallback stake for them; the reviewers dislike those. Two others gain a real stake (`c-cheap-parking-recovery`, `c-payback`, and `c-sales` carries Nadia's explicit one).
5. The presented list is no longer the engine's literal top 3. `docs/CRUX_ENGINE.md` should say so, and the skip warning lives in `quality.warnings`, which the public UI does not render, so a reader cannot see why a ranked claim is missing.
