# Round 2 — phone performance (`r2/perf`)

Date: 2026-09-29 (evening). Branch `r2/perf` off `ux/round2-2026-09-29`, with the
integration branch merged back in twice (at 4978338: legacy question headlines,
e2e, the a11y/dark pass; at c9cdad3: side audit, diagram rework) so the numbers
below are for what will ship. The final Lighthouse pass compares c451447 (the
branch's last code commit) with c9cdad3; the fuller passes before it compare
22c8d16 with 4978338.
Scope: measure the key pages in production mode on a simulated phone, find what
makes them slow, fix the biggest wins without changing the look.

## Verdict

JavaScript, main-thread work and layout shift were already fine on every page
(TBT at most 15 ms, CLS 0; no React Flow, framer-motion, `data/topics.ts` or
`data/blog.ts` in any first load of the nine pages). The phone problem was **bytes fetched before
first paint**: every page preloaded four font files (149 KB, two of them
italics most pages never draw) and fetched a 110 KB decorative watercolor at
high priority, on top of ~146 KB (gzip) of React/Next runtime. Cutting those, plus one
import mistake that shipped the topic page's client islands to home, `/about` and
`/methodology`:

- **Lighthouse mobile (simulated), final pass on what ships**: every one of the
  nine pages improves, and so does the diagram route. Score 84–87 →
  **88.5–93**; LCP 4.06–4.66 s → **3.22–3.82 s**. An earlier three-run pass
  against 4978338 agrees (score 84–87 → 85–92).
- **Applied throttling** (the same link applied in the browser): the h1 and
  lede switch to EB Garamond **0.14–0.37 s sooner** on every page, pages are
  interactive **0.5–2.1 s sooner**, and the best-run LCP is 0.1–0.4 s lower
  on all nine (the applied table shows the run-to-run noise).
- Bytes per page load: **−87 to −166 KB** on the nine pages (−13 to −28%),
  −217 KB (−37%) on the diagram.
- First Load JS: home, `/about`, `/methodology` −13 KB; the diagram route
  `/topics/[id]/map` **−64 KB** (zod, pulled in by the diagram rework that
  merged this evening; fix 6).
- The look is unchanged: first-screen screenshots of home, the AI-jobs
  flagship, the blog post and `/glossary` (after fonts and images settle) are
  pixel-identical on desktop; on a phone the only difference is the smaller
  wash image, at most 10/255 on any pixel.

## How it was measured

- `bun --bun next build` then serve (production). The baseline is the
  integration tip, built and served from a standalone copy on :3026; the
  branch on :3025.
- Lighthouse 12 (Chrome for Testing 1223), `--form-factor=mobile
  --screenEmulation.mobile`, performance only, **light colour scheme forced**
  (`--blink-settings=preferredColorScheme=1`: this Mac runs in dark mode, so
  headless Chrome otherwise renders the dark theme).
- Every pass runs **baseline and branch interleaved** page by page, so machine
  load (other agents' test suites; load average 4–40 over the evening) falls
  on both sides alike:
  1. Final: `--throttling-method=simulate` (Lantern: 150 ms RTT, 1.6 Mbps,
     4× CPU; the method PageSpeed Insights uses), c9cdad3 vs c451447, 2 runs
     each, median, 10 pages.
  2. Earlier, 4978338 vs 22c8d16: the same simulate pass with 3 runs, and
  3. `--throttling-method=devtools` (the same link applied in the browser),
     4 runs each. Lantern estimates LCP from which requests happened to finish
     before the unthrottled first paint on localhost, so it swings with local
     timing (a baseline `/learn` scored 97 in one pre-merge pass because its
     first paint happened to beat its scripts). The applied pass is the
     cross-check.
- First Load JS: Next 16's Turbopack build no longer prints it per route, so it
  is measured from the served HTML: gzip -9 of every `<script src>`, excluding
  the `noModule` polyfill modern browsers skip.

Scripts, raw Lighthouse JSON, build logs and route tables are in the session
scratch dir (`round2/perf/`: `lh2.sh`, `lh3.sh`, `lh5.sh`, `lhsum.mjs`,
`firstload.mjs`, `clientrefs.mjs`, `bgdiff.mjs`, `fontcheck.mjs`,
`lookdiff.mjs`, `mapcheck.mjs`).

## What was slow, and why

On every target page the LCP element is the serif lede under the h1 (the hero
image on the blog post). Lantern's LCP counts everything that finished loading
before first paint, so on a 1.6 Mbps link LCP was roughly the time to download
all of it. Baseline `/learn`, before first paint:

| Request | Bytes |
|---|---|
| 4 preloaded fonts (serif + sans, upright + italic) | 149 KB |
| Watercolor wash `lw-background.webp` (fetched at High priority) | 110 KB |
| First-load JS (runtime + shell + page) | ~200 KB |
| CSS (2 render-blocking files) | 25 KB |

Lighthouse's opportunities were the same on every page: render-blocking CSS
(~440 ms), unused JS (~25 KB, mostly react-dom), legacy JS (13 KB of Next's own
polyfills). Checked and clean: React Flow only loads on `/topics/[id]/map`;
framer-motion only in the `/perspectives` chunk, the lazy search modal and the
root theme provider's `MotionConfig` (inside a 5 KB gzip layout chunk); `data/topics.ts` and
`data/blog.ts` in no client chunk; lucide icons tree-shaken; every `next/image`
sized (CLS 0); the flagship hero illustration is `hidden sm:block` and lazy, so
phones never fetch it; the blog hero is `priority` with a sensible `sizes`.

## What changed

1. **`perf(fonts)`: preload only the upright faces** (`app/layout.tsx`).
   EB Garamond and Plus Jakarta Sans are variable fonts, so trimming weights
   saves nothing (one file per style covers 400–700). The waste was the italic
   styles: each family is now declared twice, upright (preloaded) and italic
   (`preload: false`). Turbopack emits both calls' `@font-face` rules under the
   same family name, so `font-style: italic` still uses the real italic face,
   fetched only when italic text is laid out. Verified with
   `CSS.getPlatformFontsForNode`: italic text renders in `EBGaramond-Italic` and
   `PlusJakartaSans-Italic`, not a synthesized slant. Preloads 4 → 2
   (149 → 72 KB). `/topics`, `/learn`, `/glossary`, the question page and the
   nuclear map download no italic file at all; the AI-jobs flagship, `/analyze`
   and the blog post fetch the serif italic only; home fetches both (it draws
   italic text in each family in its second beat, which starts inside the
   first phone screen, so that line can show the fallback italic for a moment
   on a slow connection before it swaps).
2. **`perf(wash)`: phone-size watercolor, none in dark mode**
   (`app/globals.css`, new `public/images/lw-background-sm.webp`).
   On phones the wash is drawn in a ~280 px box behind a mask that peaks at 34%
   alpha, desaturated. A 469 px copy (36 KB vs 110 KB) renders the same:
   rendered-pixel diff against the original at 412 px / DPR 1.75 is 0.10/255
   mean, 0.4% of pixels differ by more than 2 levels, none by more than 10.
   Desktop (≥768 px) keeps the original file and is pixel-identical. Dark mode
   hid the wash with `opacity: 0` but still downloaded it; it now also sets
   `background-image: none`.
3. **`perf(home)`: import crux primitives, not DebateView**
   (`components/home/homeModel.ts`, `components/FeaturedTopicHero.tsx`).
   Both imported `settleMode` and the crux-sheet class strings through
   `DebateView`'s re-exports. Importing `DebateView` put the topic page's client
   islands (`TopicActions`, `CruxReflection`: the save/share/embed code) in the
   client bundle of home and, through `homeModel`'s constants, of `/about` and
   `/methodology`. Now imported from `components/topic/cruxPrimitives`.
4. **`test(perf)`**: `app/perfContracts.test.ts` guards each fix: home's
   modules must not import `DebateView`/`TopicPage`; the italic faces are
   `preload: false` and the upright ones are not; the phone wash stays under
   50 KB; and (added with 6) the crux primitives never import the zod ledger.
5. **Merges** of `ux/round2-2026-09-29`: one conflict in `app/globals.css`,
   resolved by keeping both the phone wash rule and the a11y pass's dark-mode
   image dimming; the second merge was clean.
6. **`perf(diagram)`: keep zod out of the crux primitives' client bundle**
   (`lib/argument/ledger.ts`, new `lib/argument/ledgerProjection.ts`,
   `components/topic/cruxPrimitives.tsx`). Found after the second merge: the
   diagram rework made `cruxPrimitives` a client dependency (`DiagramDetail`,
   `MobileArgumentList`), and it imported `claimMovement` from `ledger.ts`,
   whose first line is `import { z } from "zod"`. `/topics/[id]/map` first load
   went to 244.7 KB, with a 64 KB (gzip) chunk that is mostly zod. The ledger's public projection
   (`isPublicEntry`, `publicLedgerEntries`, `currentLedgerEntries`,
   `ledgerStatus`, `claimMovement`) moves unchanged to a zod-free module;
   `ledger.ts` imports what its validator needs and re-exports the rest, so
   every existing import still works. **244.7 → 180.5 KB.** The diagram still
   draws its nodes, opens the detail panel and renders the phone list, with no
   console errors. The contract test pins both imports.

Shared files touched: `app/layout.tsx` (font declarations and the body class
only) and `app/globals.css` (one media rule, one line in the dark wash rule).
Nothing in `data/topics/*`, `lib/paste/*`, `components/paste/*` or
`lib/mapReply/*`.

## Considered and rejected

- **`experimental.inlineCss`** (would remove the two render-blocking
  stylesheets). Built and measured: Next also inlines the CSS into every RSC
  payload, so the `/learn` navigation payload went from 79 KB to 375 KB and
  every link prefetch would carry the stylesheet again. A net loss on a site
  that prefetches every visible link.
- **Dropping the preload of the upright faces.** Would lower Lantern's LCP
  further (the fonts would finish after first paint) but lengthens the
  fallback-font flash on the h1 and lede for real readers.
- **Trimming font weights.** Variable fonts: no saving.

## Left, with reasons (next wins, roughly in order)

1. **Question pages ship two unused islands (~8 KB gzip, 306 pages).**
   `app/questions/[slug]/page.tsx` imports `AgreementBlock`, `CruxSheet` and
   `PositionCards` from `components/topic/TopicPage.tsx`, which imports
   `TopicActions` and `CruxReflection` for the full page, so both ship to every
   `/questions/*` page though it renders neither. Fix: move those three section
   components (with `CruxEntry` and `MindChange`) to their own module and
   re-export them from `TopicPage.tsx`. Not done here because it moves ~290
   lines of a file the accessibility pass was editing in parallel.
2. **The AI-jobs flagship's HTML is 768 KB raw / 106 KB gzip**, the heaviest
   document on the site and the one home's rust button opens. The closed
   "Researcher mode" fold is 161 KB of its 304 KB of markup (1,133 elements),
   and the RSC payload carries it again. Rendering that fold on open, or on its
   own URL, would roughly halve the document. A product call: today it is in the
   HTML for search engines and find-in-page.
3. **`/topics` is one client component** (`TopicsPageClient` plus the topic
   index as JS, ~18 KB gzip): the heaviest target page at 198 KB. A
   server-rendered list with a small search/filter island would save ~25 KB. A
   refactor, not a surgical fix.
4. **Error boundaries.** Turbopack builds each segment's `error.tsx` as its own
   ~5 KB gzip chunk that repeats `RouteErrorState`, `Button` and `next/link`;
   nested routes load two or three (`/topics/[id]`: 15.7 KB). One boundary per
   section might do.
5. Unused `public/images/lw-background.jpg` (125 KB) is never referenced; it
   costs nothing at runtime.
