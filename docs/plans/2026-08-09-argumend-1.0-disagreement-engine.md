# Argumend 1.0 — Disagreement Engine Rebuild Plan

> Saved 2026-08-09. Founder-authored refocus plan. Reviewer addendum at the bottom.

## Objective

Refocus Argumend around one core product promise:

**Argumend should represent a contentious disagreement better than a general-purpose AI assistant can.**

The product should help a user quickly understand:

* What the major positions are
* Which claims each position depends on
* What evidence supports or challenges those claims
* Which assumptions are hidden inside the reasoning
* Where the strongest objections exist
* Which disagreements are factual, predictive, definitional, or value-based
* Which small number of unresolved propositions are the real **cruxes** of the debate
* What evidence would change the conclusion

The goal is not to declare a winner.

The goal is to make disagreement structured, inspectable, auditable, and easier to resolve.

---

# Guiding Product Principle

**Do not build "AI debate tools." Build infrastructure for representing disagreement.**

Existing features such as analysis, judging, debate generation, fallacy detection, perspective analysis, and AI scoring should become tools that operate on a shared argument model.

They should not feel like separate products.

The core system should become:

**Question → Positions → Claims → Premises → Evidence → Objections → Rebuttals → Cruxes → Uncertainty → Resolution conditions → History**

---

# North-Star Test

At the end of this project, we should be able to send someone one Argumend topic URL and have this be true:

> Within five minutes, the user understands the structure of the disagreement better than they would after reading ten conventional articles about it.

Do not optimize for number of topics, number of features, user accounts, content volume, or AI novelty until this test succeeds.

# PHASE 1 — Define the Canonical Argument Ontology

## Goal

Create a rigorous model for how Argumend represents reasoning.

This is the highest-priority technical work.

The ontology must not depend on any specific LLM or UI.

## Core node types

At minimum evaluate and formalize:

* QUESTION
* POSITION
* CLAIM
* PREMISE
* EVIDENCE
* ASSUMPTION
* INFERENCE
* COUNTERCLAIM
* OBJECTION
* REBUTTAL
* CRUX
* VALUE_JUDGMENT
* PREDICTION
* DEFINITION

Do not assume this list is perfect.

Audit the current data model and propose improvements before implementing.

## Relationship types

At minimum evaluate:

* supports
* opposes
* depends_on
* evidences
* rebuts
* undercuts
* contradicts
* qualifies
* supersedes

Relationships must have precise meanings.

For example:

An objection attacking the truth of a premise is different from an objection attacking the inference between a premise and a conclusion.

Preserve that distinction.

## Epistemic classification

Claims should be distinguishable as:

* empirical
* predictive
* normative
* definitional

Potentially add additional categories only when justified.

## Node metadata

Design a canonical schema containing fields such as:

* id
* type
* statement
* description
* scope
* confidence
* confidenceBasis
* epistemicType
* status
* assumptions
* sources
* createdAt
* updatedAt

Possible statuses:

* uncontested
* broadly_accepted
* contested
* unresolved
* superseded

Do not expose fake precision.

Confidence values must have an interpretable basis.

## Deliverables

Create:

`docs/ARGUMENT_MODEL.md`

It should define:

1. Every node type
2. Every relationship type
3. Allowed relationships
4. Epistemic categories
5. Metadata
6. Example argument graphs
7. Invalid examples
8. Guidelines for AI extraction into the schema

Then implement:

* TypeScript types
* Runtime validation
* Schema validation tests
* Migration adapters for existing topic data where practical

The ontology should become a stable contract between AI systems, stored data, APIs, and the frontend.

# PHASE 2 — Build the Crux Engine

## Goal

Make "crux identification" Argumend's signature capability.

A crux is not merely an important argument.

A crux is an unresolved proposition whose resolution would significantly change the structure or conclusion of the wider disagreement.

## Required behavior

Given an argument graph, determine:

* Which propositions are contested
* Which downstream claims depend on them
* How much of the disagreement each contested proposition affects
* Whether the disagreement is empirical, predictive, normative, or definitional
* What evidence currently bears on the proposition
* What information could potentially resolve it

## Example output

A topic may contain:

* 32 substantive claims
* 87 evidence relationships
* 14 objections

Argumend might identify:

### Crux 1

Can new nuclear plants be constructed economically?

Impacts:

* 9 downstream claims
* 2 major positions

### Crux 2

Can renewables plus storage provide equivalent reliability?

Impacts:

* 7 downstream claims
* 3 positions

### Crux 3

How should low-probability nuclear accident risk be valued?

Type:

* normative + empirical

## Algorithm

Do not simply ask an LLM:

"What are the three cruxes?"

Develop a hybrid approach using graph structure plus model reasoning.

Investigate signals such as:

* graph centrality
* dependency count
* contested status
* downstream impact
* position sensitivity
* unresolved evidence
* counterfactual effect

Use the LLM primarily for semantic interpretation.

Use deterministic graph logic wherever possible.

## Required Crux UI information

Every crux should answer:

* What is disputed?
* Why does it matter?
* Which positions depend on it?
* What evidence supports each side?
* What assumptions are embedded?
* What would change the conclusion?
* How much of the wider debate depends on this crux?

## Deliverables

Create:

`docs/CRUX_ENGINE.md`

Include:

* Definition
* Scoring approach
* Algorithm options considered
* Chosen implementation
* Limitations
* Test fixtures

Implement the first production Crux Engine.

# PHASE 3 — Build One Flagship Controversy Extremely Well

## Goal

Stop optimizing for breadth.

Prove the model on one deeply developed controversy.

Recommended initial topic:

**Should nuclear power play a substantially larger role in U.S. electricity generation?**

## Requirements

The topic should include:

* Major positions
* Major claims
* Supporting premises
* Evidence
* Counterevidence
* Objections
* Rebuttals
* Assumptions
* Predictions
* Value judgments
* Definitions
* Primary cruxes

The topic should be deep enough that an informed user can explore it for 20–30 minutes.

Do not pad the graph.

Every node should contribute meaningfully to understanding the disagreement.

## Research quality

Prioritize:

* Primary sources
* Government datasets
* Major scientific assessments
* Peer-reviewed literature
* High-quality institutional research
* Explicitly opposing credible perspectives

Avoid representing fringe objections as equivalent to mainstream evidence unless they materially affect the argument.

## Fairness testing

Use adversarial model passes.

Ask independent agents/models to argue that the representation unfairly favors:

* nuclear expansion
* anti-nuclear positions
* renewable-first positions
* economic arguments
* environmental arguments

Use their criticism to improve the map.

## Deliverable

One flagship topic that demonstrates the complete Argumend thesis.

Quality over quantity.

# PHASE 4 — Redesign Topic UX Around Progressive Disclosure

## Goal

Do not make users interpret a giant graph before understanding the controversy.

The graph should remain available, but should not necessarily be the default mental model.

## Default topic experience

A topic should first communicate:

* The question
* Major positions
* Number of meaningful claims
* Level of agreement
* Number of unresolved cruxes
* The primary cruxes
* What has changed recently, when applicable

Example:

**Should the U.S. substantially expand nuclear power?**

4 major positions
31 substantive claims
68 evidence items
3 primary unresolved cruxes

### The debate mostly comes down to:

1. Can nuclear be built economically?
2. Can renewables + storage provide equivalent reliability?
3. How should nuclear risk be valued?

Each crux should be expandable.

Only then should the user descend into supporting reasoning.

## Progressive layers

### Layer 1

Understand the debate.

### Layer 2

Understand a crux.

### Layer 3

Inspect its claims and evidence.

### Layer 4

Inspect the full graph.

The existing React Flow implementation should become the **Full Map** mode rather than carrying the entire product experience.

## Deliverable

A redesigned flagship topic experience demonstrating progressive disclosure.

# Mobile-First Mandate (founder amendment, 2026-08-09)

90%+ of the traffic Argumend should be trying to engage is mobile. A shared topic link gets opened on a phone, from a chat app or social feed. If the first paint is a pannable graph canvas on a 390px screen, the north-star test fails before it starts.

Implications:

* The Phase 4 progressive-disclosure experience IS the mobile experience. Design it at 390px first; desktop is the enhancement.
* Layer 1–3 (debate summary → crux → claims and evidence) must work as vertical scroll and tap — no panning, no pinch-to-understand.
* The full React Flow map is a desktop/tablet enhancement (Layer 4). On phones it can be demoted or omitted. The current state — `MobileArgumentList` as a fallback because the graph can't work on phones — has this backwards: mobile is the primary experience, not the degraded one.
* Performance budget is a mobile budget: test on throttled connections; keep the topic payload lean; preserve the existing pattern of never shipping the canvas bundle to mobile sessions.
* The north-star test is run on a phone.

# PHASE 5 — Make Evidence a First-Class System

## Goal

Build provenance into the argument structure.

Evidence should not exist as text citations appended to AI claims.

Evidence should be its own reusable object.

## Evidence model

Evaluate fields such as:

* id
* title
* author
* institution
* publication date
* URL
* publication type
* primary/secondary source
* peer reviewed
* relevant passage or finding
* methodology
* dataset
* limitations
* current/superseded/retracted status
* supported claims
* challenged claims

## Relationships

One source may support multiple claims.

One claim may have:

* supporting evidence
* conflicting evidence
* qualifying evidence
* superseded evidence

The system should explicitly model these relationships.

## UI requirement

A user should be able to start at a claim and inspect:

* supporting evidence
* conflicting evidence
* evidence quality
* source provenance
* source date
* why the evidence is relevant

The AI must explain the relationship rather than simply attach links.

## Source integrity

Preserve and extend the repository's existing source validation infrastructure.

## Deliverable

A reusable evidence subsystem integrated into the flagship controversy.

# PHASE 6 — Reframe Existing AI Features Around the Graph

## Goal

Existing AI capabilities should operate on the common argument graph instead of appearing as unrelated features.

### Analyze

New role:

**Convert material into the Argumend ontology.**

Inputs may include:

* text
* article
* transcript
* debate
* user-written argument

Output should be structured nodes and relationships.

### Debate

New role:

**Stress-test an argument graph.**

An AI opponent should identify:

* unsupported claims
* weak premises
* missing objections
* questionable inference steps
* ignored evidence

### Judging

Move away from:

**Winner / loser / 74 vs 51**

Toward:

* reasoning strength
* evidentiary support
* unresolved objections
* dependence on uncertain premises
* contradiction
* invalid inference
* unsupported confidence

Avoid presenting Argumend as an oracle.

### Fallacy detection

New role:

Annotate specific reasoning relationships.

A fallacy should be attached to the actual inference where it occurs.

### Perspective analysis

New role:

Show how different frameworks change:

* assumptions
* values
* priorities
* interpretations

Do not treat a perspective as evidence.

## Deliverable

A coherent architecture where these systems modify, inspect, or stress-test the same underlying argument model.

# PHASE 7 — Versioning and Argument History

Do this only after the earlier phases work well.

## Goal

Track how justified beliefs and disagreement evolve.

Do not regenerate a topic and overwrite its history.

Record meaningful changes.

## Example

### Crux

Can utility-scale storage economically provide multiday backup?

2026 — High uncertainty
2027 — Moderate supporting evidence
2029 — Major deployment evidence
2031 — Strong support

Users should be able to inspect:

**What changed?**

Possible change types:

* new evidence
* superseded evidence
* failed prediction
* successful prediction
* new objection
* resolved objection
* changed confidence
* altered dependency

## Long-term opportunity

Allow questions such as:

* What was reasonable to believe using evidence available in 2020?
* Which arguments aged well?
* Which predictions failed?
* Which cruxes have actually been resolved?
* Why did consensus change?

## Deliverable

A first versioned argument history model.

# Quality Rules

The following principles should guide all implementation decisions.

### 1. Auditable over authoritative

Argumend should explain why something is weak or strong.

Avoid requiring users to trust an unexplained verdict.

### 2. Structure over prose

Prefer explicit argument relationships over long AI summaries.

### 3. Cruxes over volume

Five meaningful disagreements are more valuable than fifty generic claims.

### 4. Provenance over confidence theater

Do not show confidence numbers without interpretable support.

### 5. Progressive disclosure

Users should understand the big picture before seeing complexity.

### 6. Persistent knowledge over disposable generations

Prefer reusable claims, evidence, and relationships over generating a new answer for every page view.

### 7. Fair representation

The strongest credible version of opposing arguments should be represented.

### 8. Separate facts from values

The system must distinguish empirical disagreement from normative disagreement.

### 9. Preserve uncertainty

Do not force unresolved questions into binary conclusions.

### 10. Optimize for understanding

The graph, AI, UI, evidence system, and scores exist to help users understand what the disagreement actually depends upon.

# Argumend 1.0 Definition of Done

Argumend 1.0 is ready when one flagship controversy can demonstrate all of the following:

* Major positions are represented fairly
* Claims are structurally decomposed
* Evidence is traceable
* Assumptions are visible
* Objections attack specific propositions or inferences
* Rebuttals are connected correctly
* Factual and value disagreements are distinguishable
* The system identifies a small set of meaningful cruxes
* Each crux explains what would resolve it
* Users can understand the controversy without opening the full graph
* Users can inspect the full reasoning when desired
* AI-generated analysis maps into the same ontology
* Argumend does not rely on unexplained winner/loser scores
* Sign-in is unnecessary for the main experience
* The full experience (Layers 1–3) works excellently on a phone; the graph is optional to the mobile journey
* The north-star test passes when run on a mobile device
* The flagship topic provides substantially more insight than asking a general-purpose chatbot for a summary of both sides

The goal of this cycle is not to finish Argumend.

The goal is to prove the core invention:

**Every disagreement has a structure. Argumend maps it.**

# Reviewer Addendum (Claude, 2026-08-09)

The plan is endorsed. Three risks worth holding onto, from repo history:

1. **This is the 7th major plan in `docs/plans/`, and the recurring failure mode has been building in a vacuum, not building the wrong thing.** The north-star test requires a human on the other end of the URL, but the implementation order doesn't put one there until ~8 phases are done. Mitigation: run the north-star test **now**, as a baseline, with the existing nuclear topic (see `2026-06-22-nuclear-flagship-journey-design.md`) — a handful of real people, five minutes, Argumend URL vs. asking a chatbot. Repeat the same test after each phase ships. If a phase doesn't move that test, question the next phase.

2. **Ontology paralysis is the historical graveyard of argument-mapping projects** (IBIS, Compendium, Debategraph, Kialo's early iterations). 14 node types + 9 edge types is a lot. Timebox Phase 1, bias toward fewer types, and let the flagship topic's real content force which distinctions earn their place — spec and content should be built in dialogue, not sequence.

3. **Suggested sequencing tweak:** pull flagship-topic research (Phase 3 / Package F) forward to run in parallel with the ontology work. Research is the long pole, it doesn't depend on the schema, and concrete material is the best test of whether the ontology is right.

**Follow-up (same day):** Founder's response to point 1: the bet is that a genuinely compelling formula self-propagates — get movement on how people perceive one controversial topic and the knock-on effect grows the corpus. Accepted as the working strategy; the phase-by-phase north-star test remains the cheap check on whether the formula is actually hitting a nerve. Founder also added the Mobile-First Mandate above: the sharing surface is a phone, so a desktop-canvas-first product structurally caps distribution regardless of quality.

**Follow-up (2026-08-10):** Phase 3's recommended topic changed by founder decision: the flagship is now **AI and jobs** ("Will AI cause mass unemployment?") — nuclear proved insufficiently tribal in 2026 (baseline link-drop responses were muted; Wave 1 research documented bipartisan nuclear support). Nuclear's completed research corpus becomes the second deep topic. A third, maximum-heat target (America's support for Israel / the Iran strikes) is parked until the flagship demonstrates fairness credibility. Details in `docs/plans/2026-08-10-argumend-1.0-execution-plan.md` § Amendments.
